# atomic-prompts — Claude Code skill

> Generates `atomic-prompts/NNNN-<slug>.md` from a loose user idea. Does NOT implement the idea.

## Triggers

- `/atomic-prompts <idea>`
- `use the atomic-prompts skill for "<idea>"`
- `run /atomic-prompts on: <idea>`
- Multi-line:
  ```
  /atomic-prompts
  <multi-line idea>
  ```

## Behaviour contract

1. **Read context first.** `PROJECT_MAP.md`, `STATE.md`, `PROJECT_RULES.md`, plus the topic-specific rule file (`DESIGN.md` / `DATABASE.md` / `CODING_RULES.md` / `DEPLOYMENT.md` / `PRODUCT.md`). Do not full-scan the repo.
2. **Resolve next ID.** Scan `atomic-prompts/` for files matching `^\d{4}-`. Use the highest existing number + 1, zero-padded to 4 digits. Start at `0001` if the folder is empty.
3. **Slug.** Lowercase, hyphen-separated, ASCII, ≤ 60 chars, derived from the idea.
4. **Write** `atomic-prompts/<ID>-<slug>.md` using the **Output schema** below.
5. **Print** confirmation:
   ```
   Created: atomic-prompts/<ID>-<slug>.md
   Acceptance criteria: <count>
   References: PROJECT_MAP.md §<n>, STATE.md §<n>, PROJECT_RULES.md §<n>
   ```
6. **Stop.** Do not implement.

## Hard rules

- ❌ Never implement the idea inline. Only produce the prompt file.
- ❌ Never write outside `atomic-prompts/`.
- ❌ Never duplicate the body of other doc files — reference them.
- ❌ Never silently omit sections 7 / 8 / 11 — write `**N/A** — <one-line reason>` instead.
- ❌ Never invent file paths absent from `PROJECT_MAP.md` without marking them `(new)`.
- ✅ Acceptance criteria are verifiable / observable (no "looks good", no "is fast").
- ✅ Always include the documentation-updates checklist (section 10).
- ✅ Target 4–10 acceptance criteria per prompt.

## Output schema

````markdown
# <<ID>> — <<imperative title>>

> Generated by atomic-prompts skill on <<DATE>>. Source idea: "<<RAW_IDEA>>"

## 1. Goal
<<one paragraph, plain language; outcome, not method>>

## 2. Context (read first)
- Source-of-truth files this depends on:
  - PROJECT_MAP.md §<<n>> — <<why>>
  - STATE.md §<<n>> — <<why>>
  - <<TOPIC_RULE_FILE>> §<<n>> — <<why>>
- Recent decisions / background: <<bullets or N/A>>
- Explicit non-context: <<things to NOT bring in>>

## 3. Scope
**In scope**
- <<bullet>>

**Out of scope**
- <<bullet>>

## 4. Files likely to be touched
| Path | Change | Notes |
| ---- | ------ | ----- |
| <<path>> | new/edit/delete/rename | <<short note>> |

## 5. Step-by-step plan
1. <<step>>
2. <<step>>

## 6. Acceptance criteria
- [ ] <<verifiable, observable>>

## 7. Edge cases & failure modes
- <<edge case>> — <<expected behaviour>>
*(or **N/A** — <reason>)*

## 8. Security / privacy notes
- New secrets / PII / permission boundary?
- `.env.example` / `DATABASE.md` / `PROJECT_RULES.md` updates required?
*(or **N/A** — <reason>)*

## 9. Test plan
- Manual steps
- Automated tests (unit / integration / e2e / none)
- Tools needed

## 10. Documentation updates
- [ ] STATE.md
- [ ] CHANGELOG.md (append, tagged `(prompt: <<ID>>)`)
- [ ] CLIENT_DOCS.md (if client-visible)
- [ ] PROJECT_MAP.md (if structure changes)
- [ ] RELEASE_NOTES.md (if part of next release)

## 11. Rollback plan
- <<how to back out>>
*(or **N/A** — <reason>)*

## 12. References
- <<links / screenshots / earlier prompts>>
````

## When the idea is unclear

- If the idea touches **>5 files**, suggest splitting and ask which half to generate first.
- If the idea is **too vague to localise** ("make it better"), ask ONE clarifying question with 3–4 candidate sub-ideas, then proceed.
- If the idea **violates `PROJECT_RULES.md`** (new framework, secret on the client, edits to past `CHANGELOG.md` entries), flag the conflict and wait for the user's call.
