# atomic-prompts — Codex CLI skill

> Generates `atomic-prompts/NNNN-<slug>.md` from a loose user idea. Does NOT implement the idea.

## Triggers

- `/atomic-prompts <idea>`
- `use the atomic-prompts skill for "<idea>"`
- `run /atomic-prompts on: <idea>`
- Multi-line:
  ```
  /atomic-prompts
  <multi-line idea>
  ```

## Behaviour contract

1. Read `PROJECT_MAP.md`, `STATE.md`, `PROJECT_RULES.md` and the topic-specific rule file (`DESIGN.md` / `DATABASE.md` / `CODING_RULES.md` / `DEPLOYMENT.md` / `PRODUCT.md`). Do not full-scan the repo.
2. Resolve the next 4-digit zero-padded ID by scanning `atomic-prompts/` for files matching `^\d{4}-`. Start at `0001` if empty.
3. Build a slug: lowercase, hyphen-separated, ASCII, ≤ 60 chars.
4. Write `atomic-prompts/<ID>-<slug>.md` using the **Output schema** below.
5. Print a one-block confirmation: path, AC count, references.
6. Stop. Do not implement.

## Hard rules

- ❌ Never implement the idea inline.
- ❌ Never write outside `atomic-prompts/`.
- ❌ Never duplicate other doc files — reference them.
- ❌ Never silently omit sections 7 / 8 / 11 — write `**N/A** — <one-line reason>`.
- ❌ Never invent file paths missing from `PROJECT_MAP.md` without marking them `(new)`.
- ✅ Acceptance criteria are verifiable / observable.
- ✅ Always include the doc-updates checklist (section 10).
- ✅ Target 4–10 acceptance criteria per prompt.

## Output schema

````markdown
# <<ID>> — <<imperative title>>

> Generated by atomic-prompts skill on <<DATE>>. Source idea: "<<RAW_IDEA>>"

## 1. Goal
<<one paragraph, plain language; outcome not method>>

- Source-of-truth files:
  - PROJECT_MAP.md §<<n>> — <<why>>
  - STATE.md §<<n>> — <<why>>
  - <<TOPIC_RULE_FILE>> §<<n>> — <<why>>
- Background: <<bullets or N/A>>
- Explicit non-context: <<what NOT to bring in>>

## 3. Scope
**In scope**
- <<bullet>>

**Out of scope**
- <<bullet>>

## 4. Files likely to be touched
| Path | Change | Notes |
| ---- | ------ | ----- |
| <<path>> | new/edit/delete/rename | <<note>> |

## 5. Step-by-step plan
1. <<step>>
2. <<step>>

## 6. Acceptance criteria
- [ ] <<verifiable, observable>>

## 7. Edge cases & failure modes
- <<edge case>> — <<expected behaviour>>
*(or **N/A** — <reason>)*

## 8. Security / privacy notes
- Secrets / PII / permission boundary?
- `.env.example` / `DATABASE.md` / `PROJECT_RULES.md` updates required?
*(or **N/A** — <reason>)*

## 9. Test plan
- Manual steps
- Automated tests (unit / integration / e2e / none)

## 10. Documentation updates
- [ ] STATE.md
- [ ] CHANGELOG.md (append, `(prompt: <<ID>>)`)
- [ ] CLIENT_DOCS.md (if client-visible)
- [ ] PROJECT_MAP.md (if structure changes)
- [ ] RELEASE_NOTES.md (if in next release)

## 11. Rollback plan
- <<how to back out>>
*(or **N/A** — <reason>)*

## 12. References
- <<links / screenshots / earlier prompts>>
````

## When the idea is unclear

- If the idea touches **>5 files**, suggest splitting and ask which half first.
- If the idea is **too vague** ("make it better"), ask ONE clarifying question with 3–4 candidate sub-ideas, then proceed.
- If the idea **violates `PROJECT_RULES.md`**, flag the conflict and wait for the user's call.
